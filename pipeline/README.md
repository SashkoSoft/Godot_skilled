# Пайплайн ассетов: Godot-сессия ↔ Houdini-сессия

Это общее место обмена между двумя сессиями Claude Code:

- **Godot-сессия** (эта) — делает игру, формулирует, какие ассеты нужны, принимает и
  интегрирует результат.
- **Houdini-сессия** — крутится в `/loop`, забирает задания, генерирует ассеты, кладёт файлы
  обратно. Её пошаговая инструкция — `HOUDINI_LOOP.md`, требования к файлам — `ASSET_SPEC.md`.

Обе стороны общаются **только через файлы в этой папке**. Никто не правит чужие файлы:
задания пишет Godot-сессия, результаты — Houdini-сессия.

## Схема

```
pipeline/
  tasks/
    open/           ← Godot кладёт задание сюда          (Houdini: читать)
    in_progress/    ← Houdini переносит взятое в работу  (Godot: не трогать)
    done/           ← Houdini переносит выполненное      (Godot: принимает)
    blocked/        ← Houdini: не могу / нужны уточнения (Godot: отвечает)
    TEMPLATE.md     — шаблон задания
  delivery/
    <task-id>/      ← готовые файлы + RESULT.md от Houdini
  QUEUE.md          — доска состояния, ведёт Houdini
  ASSET_SPEC.md     — технические требования к ассетам (форматы, оси, PBR, лимиты)
  HOUDINI_LOOP.md   — что делать Houdini-сессии на каждой итерации
```

**Папка = статус.** Одно задание — один файл, который переезжает между папками.
Дублировать статус ещё где-то не надо: рассинхрон дороже удобства.

## Жизненный цикл задания

1. **Godot-сессия** создаёт `tasks/open/task-0007-lava-texture.md` по `TEMPLATE.md`.
   Номер — следующий свободный, сквозной по всем папкам.
2. **Houdini-сессия** на очередной итерации лупа берёт **самое старое** задание из `open/`,
   переносит файл в `in_progress/`, дописывает в него строку `started:` с датой.
3. Houdini генерирует ассеты, кладёт их в `delivery/task-0007-lava-texture/`
   вместе с `RESULT.md` (что сделано, параметры, чем открыть, что можно докрутить).
4. Houdini переносит задание в `done/`, ставит `status: done`, обновляет `QUEUE.md`.
5. **Godot-сессия** забирает файлы из `delivery/<task-id>/`, проверяет их в движке,
   копирует в проект игры и пишет вердикт в конце файла задания в `done/`
   (раздел «Приёмка»). Если ассет не подошёл — заводит **новое** задание со ссылкой
   на старое, а не переоткрывает закрытое.

Если задание непонятно или невыполнимо — Houdini переносит его в `blocked/`, ставит
`status: blocked` и пишет в разделе «Вопросы», чего не хватает. Godot-сессия отвечает
в том же файле и возвращает его в `open/`.

## Синхронизация между сессиями

Обе сессии работают с одним репозиторием `git@github.com:SashkoSoft/Godot_skilled.git`.

- **Одна машина, одна папка** — ничего синхронизировать не нужно, файлы общие.
  Осторожно с одновременной правкой одного файла: за задание в `in_progress/` отвечает
  только Houdini, за `open/` — только Godot.
- **Разные папки или машины** — каждая итерация лупа начинается с `git pull --rebase`
  и заканчивается `git add pipeline && git commit && git push`. Коммит одной итерации —
  один: перенос задания + файлы доставки + `QUEUE.md`.

Конфликтов почти не бывает, потому что стороны пишут в разные папки. Если конфликт всё же
случился в `QUEUE.md` — он информационный, чинится в пользу более свежей версии.

## Вес файлов

Обычный git, без LFS. Правила:

- Один файл — **до 50 МБ**, вся доставка по заданию — **до 200 МБ**.
- Не класть в репозиторий: кэши симуляций, `.bgeo`-сиквенции, промежуточные рендеры,
  исходные `.hip` тяжелее 20 МБ.
- Если результат честно не влезает — Houdini пишет об этом в `RESULT.md` и кладёт
  в `delivery/` уменьшенную версию (например, 2K вместо 8K), а полную оставляет локально
  и указывает путь. Тогда решаем, включать ли Git LFS.

## Что уже готово к использованию

- `ASSET_SPEC.md` — форматы и требования, сверенные с документацией Godot 4.7
  (`docs/godot-docs`). Houdini-сессии достаточно читать этот файл, знать Godot ей не нужно.
- `TEMPLATE.md` — шаблон задания с обязательными полями.
- Пример полного цикла — в `HOUDINI_LOOP.md`.
