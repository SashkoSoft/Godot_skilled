# Пайплайн ассетов: Godot-сессия ↔ Houdini-сессия

Это общее место обмена между двумя сессиями Claude Code:

- **Godot-сессия** (эта) — делает игру, формулирует, какие ассеты нужны, принимает и
  интегрирует результат.
- **Houdini-сессия** — крутится в `/loop`, забирает задания, генерирует ассеты, кладёт файлы
  обратно. Её пошаговая инструкция — `HOUDINI_LOOP.md`, требования к файлам — `ASSET_SPEC.md`.

Обе стороны общаются **только через файлы в этой папке**. Никто не правит чужие файлы:
задания пишет Godot-сессия, результаты — Houdini-сессия.

## Схема

```
pipeline/
  tasks/
    open/           ← Godot кладёт задание сюда          (Houdini: читать)
    in_progress/    ← Houdini переносит взятое в работу  (Godot: не трогать)
    done/           ← Houdini переносит выполненное      (Godot: принимает)
    blocked/        ← Houdini: не могу / нужны уточнения (Godot: отвечает)
    TEMPLATE.md     — шаблон задания
  delivery/
    <task-id>/      ← готовые файлы + RESULT.md от Houdini
  QUEUE.md          — доска состояния, ведёт Houdini
  ASSET_SPEC.md     — технические требования к ассетам (форматы, оси, PBR, лимиты)
  HOUDINI_LOOP.md   — что делать Houdini-сессии на каждой итерации
```

**Папка = статус.** Одно задание — один файл, который переезжает между папками.
Дублировать статус ещё где-то не надо: рассинхрон дороже удобства.

## Жизненный цикл задания

```
   Godot                         Houdini
   ─────                         ───────
   open/  ──────────────────►    in_progress/
                                      │  делает ассет
                                      ▼
   done/  ◄──────────────────    delivery/<task-id>/v1/ + RESULT.md
     │
     ├─ принято  →  задание остаётся в done/, ассет уходит в игру
     └─ на переделку → open/ (revision: 2, раздел «Правки»)
```

1. **Godot-сессия** создаёт `tasks/open/task-0007-lava-texture.md` по `TEMPLATE.md`.
   Номер — следующий свободный, сквозной по всем папкам (`bash pipeline/status.sh`
   печатает его).
2. **Houdini-сессия** на очередной итерации лупа берёт **самое старое** задание из `open/`,
   переносит файл в `in_progress/`, ставит `started:`.
3. Houdini генерирует ассеты, кладёт их в `delivery/task-0007-lava-texture/v1/`
   вместе с `RESULT.md` (что сделано, параметры, отклонения от задания).
4. Houdini переносит задание в `done/`, ставит `status: done` и `finished:`, пушит.
5. **Godot-сессия** делает `git pull`, забирает файлы из `delivery/<task-id>/v<N>/`,
   проверяет их в движке и пишет вердикт в раздел «Приёмка» файла задания:
   - **Принято** → `status: accepted`, файл остаётся в `done/`, ассет копируется в игру.
   - **На переделку** → в разделе «Правки» перечисляется, что не так; `revision`
     увеличивается на 1, `status: open`, файл **возвращается в `open/`**.
     Houdini берёт его следующей итерацией и кладёт результат в `v2/` — предыдущая
     версия остаётся на месте, её видно рядом для сравнения.

Переделка — обычная часть цикла, а не авария. Новое задание заводится только тогда,
когда нужен **другой** ассет, а не другая версия этого.

Если задание непонятно или невыполнимо — Houdini переносит его в `blocked/`, ставит
`status: blocked` и пишет в разделе «Вопросы», чего не хватает. Godot-сессия отвечает
в том же файле и возвращает его в `open/`.

## Синхронизация: разные папки, обмен через git

Рабочий режим: **у каждой сессии свой клон** репозитория
`git@github.com:SashkoSoft/Godot_skilled.git`, обмен — только через `push`/`pull`.

- Houdini-сессия начинает итерацию с `git pull --rebase` и заканчивает одним коммитом:
  перенос файла задания + доставка. Затем `git push`.
- Godot-сессия делает `git pull` перед тем, как смотреть доставки, и пушит свои
  вердикты приёмки и новые задания.
- Если `push` отклонён (другая сторона успела раньше) — `git pull --rebase` и `push`
  ещё раз. Стороны пишут в разные файлы, поэтому ребейз проходит без конфликтов.

Что делает конфликты почти невозможными:

| Файл | Кто пишет |
|---|---|
| `tasks/open/*` | Godot (создаёт, возвращает на переделку) |
| `tasks/in_progress/*`, `tasks/done/*` (перенос, `status`, `finished`) | Houdini |
| раздел «Приёмка» и «Правки» в файле задания | Godot |
| раздел «Вопросы», `tasks/blocked/*` | Houdini |
| `delivery/**` | Houdini (Godot только читает) |
| `QUEUE.md` | никто вручную — генерируется `pipeline/status.sh` |

Единственный момент, когда обе стороны трогают один файл, — файл задания. Но пишут они
в **разные разделы** и в разное время (Godot — только когда задание в `done/`), так что
git сливает это автоматически.

`QUEUE.md` не ведётся руками: `bash pipeline/status.sh` перечитывает файлы заданий и
перезаписывает таблицу. При конфликте в нём — просто перегенерировать.

## Вес файлов

Обычный git, без LFS. Правила:

- Один файл — **до 50 МБ**, вся доставка по заданию — **до 200 МБ**.
- Не класть в репозиторий: кэши симуляций, `.bgeo`-сиквенции, промежуточные рендеры,
  исходные `.hip` тяжелее 20 МБ.
- Если результат честно не влезает — Houdini пишет об этом в `RESULT.md` и кладёт
  в `delivery/` уменьшенную версию (например, 2K вместо 8K), а полную оставляет локально
  и указывает путь. Тогда решаем, включать ли Git LFS.

## Что уже готово к использованию

- `ASSET_SPEC.md` — форматы и требования, сверенные с документацией Godot 4.7
  (`docs/godot-docs`). Houdini-сессии достаточно читать этот файл, знать Godot ей не нужно.
- `TEMPLATE.md` — шаблон задания с обязательными полями.
- Пример полного цикла — в `HOUDINI_LOOP.md`.
