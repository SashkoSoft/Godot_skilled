# .glb без текстуры: диагностика и фикс

## Два способа хранить текстуру в .glb

glTF-модель ссылается на текстуру одним из двух способов, и снаружи (в
Godot-редакторе, на превью) они выглядят одинаково, пока текстура на месте:

- **встроено бинарно** — картинка лежит внутри самого `.glb`, файл
  самодостаточен. Проверяется так: `strings model.glb | grep -i '\.png'` —
  если пусто, значит встроено (или ссылки нет вообще).
- **внешней ссылкой (`uri`)** — материал хранит просто имя файла
  (`"bedroom_albedo_1k.png"`), и картинка должна физически лежать **рядом**
  с `.glb` на диске. Если её там нет — `StandardMaterial3D.albedo_texture`
  молча становится `null`, без единой ошибки в консоли.

Разобрать без Godot, напрямую по байтам (glTF-JSON — первый chunk бинарного
`.glb`):

```python
import struct, json
with open("model.glb", "rb") as f:
    data = f.read()
length = struct.unpack_from("<I", data, 8)[0]
off = 12
while off < length:
    chunk_len, chunk_type = struct.unpack_from("<I4s", data, off)
    off += 8
    chunk_data = data[off:off+chunk_len]
    off += chunk_len
    if chunk_type == b"JSON":
        j = json.loads(chunk_data.decode("utf-8"))
        print(j.get("images"))  # [{"uri": "..."}] или пусто/embedded
```

Внешние ссылки удобны исполнителю (несколько `.glb` делят один атлас без
дублирования), но именно поэтому **интегрирующая сессия обязана копировать
текстуры вместе с моделью**, а не только `.glb` — это самая частая причина
«текстуры нет» в таком пайплайне.

## Второй источник той же ошибки: имя не совпадает

Даже когда PNG рядом скопирован, привязка может не сработать, если имя в
самом `.glb` не совпадает буквально с именем файла на диске. В этом проекте
дважды подряд один и тот же экспорт-баг: модель ссылалась на
`..._albedo_1k.png`, а по спеке и факту был сдан атлас `..._albedo_512.png`
— другое разрешение, другое имя файла. Разбор `images[].uri` (см. выше) —
единственный надёжный способ узнать точное ожидаемое имя, не гадать по
аналогии с другими моделями того же исполнителя.

Если актив уже принят и стоит в сцене (баг обнаружился только сейчас) —
проще добавить копию файла под именем, которого ждёт `.glb`, чем ждать
переделки: это интеграционный фикс, не полноценный костыль, он ничего не
скрывает и снова подсветится числом при следующей проверке. Если актив ещё
на приёмке — вернуть с точным указанием, какое имя внутри `.glb` не
совпадает с чем.

## Godot не переимпортирует зависимость сама

`--headless --path <проект> --import` подхватывает новые файлы, но если вы
добавили PNG, которого раньше не было, а `.glb`, ссылающийся на неё, уже
когда-то импортировался (с `albedo=null` в кеше) — повторный `--import`
**не** заставит Godot перечитать именно этот `.glb`. Кеш `.import` считает,
что зависимости не изменились. Лечится только явно:

```bash
rm path/to/model.glb.import
Godot_console.exe --headless --path <проект> --import
```

После этого — обязательно перепроверить числом (см.
`numeric-verification.md`), не полагаться, что раз ошибок в консоли нет,
значит починилось.

## headless — не для всего

- `--probe=`, `--texcheck=`, `--meshcheck=` (или любой аналогичный CLI-флаг,
  который только читает данные модели/текстуры без рисования кадра) —
  безопасны под `--headless`, и это предпочтительный режим: быстрее,
  без GPU-контекста, без риска зависшего окна.
- Любой реальный рендер (`--shot=`, скриншот, `--asset=...--debug=`) —
  **требует настоящего GPU-контекста**, `--headless` тут не подходит: окно
  либо не создастся вообще, либо процесс тихо повиснет без вывода и без
  выхода (не упадёт, не напечатает ошибку — просто не завершится). Разница
  на глаз незаметна: обе команды одинаково «ничего не пишут в консоль»,
  различить можно только по факту — процесс с `--headless` для рендера
  либо сразу не даёт файла, либо висит куда дольше, чем должен бы занимать
  реальный рендер сцены такого размера.
